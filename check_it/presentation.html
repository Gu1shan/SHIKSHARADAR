The Innovation

Mistake Fingerprinting

Every student develops a pattern of errors across assessments. Shiksha Radar fingerprints that pattern — by concept and by error type — over time.

Traditional view

"Student scored 60% on Fractions"

Shiksha Radar view

"Fractions → 7 errors across 3 assessments (84% confidence)
 ├─ Denominator handling: 5 (recurring, ↑ trend)
 ├─ Simplification: 1 (isolated)
 └─ Addition: 1 (careless)
 → Equivalent fractions review + 5 targeted problems"

Why this is different

  • Not a marks dashboard, attendance tracker, chatbot, or generic tutor.
  • Not predicting "who will fail" — it reports which concepts show repeated difficulty, the evidence, and what might help.
  • Deterministic, auditable core + guarded LLM layer = explainable by design.
What Makes It Different

Not a dashboard, not a chatbot, not a predictor

It is NOT

  • A marks dashboard or attendance tracker
  • A generic AI tutor or chatbot
  • A "who will fail" prediction engine
  • A replacement for the teacher

It IS

  • Concept-granular — which concept, which error type
  • Longitudinal — patterns across assessments
  • Evidence-cited — every claim shows counts + confidence
  • Decision-supporting — the teacher stays in charge
Core positioning: it reports "which concepts show repeated difficulty, the evidence, and what might help" — never "this child will fail."

Deliberate Exclusions

What is NOT in the stack — and why

Excluded from MVP/SIH

  • Docker / Kubernetes — no benefit at prototype scale; adds real complexity
  • React / Node — Streamlit delivers the demo with zero frontend code
  • Heavy ML / deep learning — deterministic rules + statistics are more auditable and sufficient
  • PostgreSQL — SQLite covers prototype needs; upgrade only when scaling

Rule: every technology must have a reason

Each tool maps to a concrete job: Pandas reads data, Streamlit shows it, embeddings map concepts, LLM explains, SQLite remembers. No tool is included for its name.

This keeps the beginner buildable and the demo honest — "actually impressive because it works."

AI Architecture

Where AI is used — and where it is NOT

✓ Good uses (LLM gets structured evidence)

  • Explain detected patterns in plain language
  • Summarize class insights for teachers
  • Generate targeted practice questions
  • Suggest interventions
  • Translate explanations (Hindi, regional)
  • Map natural-language answers to concepts

✗ Bad uses (never)

  • Blindly deciding a child is "weak"
  • Making unsupported predictions
  • Replacing deterministic calculations
  • Storing sensitive student info in prompts
  • Generating unexplained risk scores
Structured evidence JSON → Prompt template → LLM → Teacher-friendly explanation
Guardrails: no names · cite evidence · show confidence · "may benefit" not "will fail"
Hallucination control: low temperature · validated output · template fallback on failure
LLM Layer

Prompt architecture — evidence in, explanations out

[CONTEXT]
  Student pseudonymized (Student_001), Grade 5, Mathematics
  - Assessment window: 2026-03-01 → 2026-06-01
  - Confidence of finding: 84% (7 errors / 8 responses over 3 assessments)
[STRUCTURED FINDINGS — JSON]
  {"concept": "fractions", "error_type": "denominator_handling",
   "error_count": 7, "recurring": true, "trend": "increasing",
   "confidence": 0.84, "evidence": [{"q": "Q12", "topic": "add_fractions", "error": "wrong_common_denominator"}]}
[TASK]
  Explain this finding to a teacher in 3 sentences. Plain language.
  State the confidence. Suggest one concrete review activity.
  Do NOT invent claims. If unsure, say "unclear".
Guardrails: temperature ≤ 0.2 · structured JSON schema · evidence must cite question IDs · "unsure → say unclear" · nothing outside the provided JSON.
Trust Controls

Hallucination & bias controls

Hallucination control

  • LLM sees only structured evidence — never raw PII
  • Strict output schema; rejected outputs are retried ≤ 2×
  • Every explanation displays a citation block + confidence
  • Rule-based layer unaffected if LLM is offline

Bias & fairness control

  • No ethnicity/income/locale features in detection
  • Thresholds uniform per concept, not per student
  • Equity drill-down compares support needs by class/cohort, never names
  • Language approved: "possible learning gap", "may benefit from additional support", "confidence: X%"
Forbidden language: never "weak", "bad", "failing", "at risk", "hopeless". Findings are probabilistic hypotheses backed by evidence, reviewable by the teacher.
Mistake Detection

A deterministic, evidence-first algorithm

Question → Expected answer → Student answer
              ↓
        Normalization (case, spaces, unicode, ±0.01 tolerance)
              ↓
        Comparison → correct / incorrect
              ↓
        Error category (rule-based, auditable)
              ↓
        Concept (rules → embeddings → teacher-review flag)

Error taxonomy

Conceptualmisconception, wrong approach, formula selection
Proceduraldenominator, sign error, simplification, decimal placement, units
Calculationarithmetic, multiplication/division facts
Carelessincomplete, misread, copy error
Unknownambiguous, blank
Honest limit: one answer cannot reveal a child's psychology. Shiksha Radar only claims patterns observed across multiple assessments, with a confidence score.
The Core Engine

Mistake Fingerprinting — the algorithm

For every student, for every assessment:
  analyze each answer → assign {concept, correctness, error_type}

Aggregate over time:
  • error frequency          (count + rate)
  • recurrence               (assessments with errors)
  • recent trend             (slope of error rate)
  • concept coverage         (attempts per concept)
  • confidence               (0–1)

Confidence = min(0.95, Wilson_lower_bound(error_rate, n) × recency_weight)

Gap detection thresholds:
  total_errors ≥ 3  AND  assessments_with_errors ≥ 2  AND  confidence ≥ 0.70

Output: LearningGap(student, concept, dominant_error, evidence, confidence, trend)

Advanced (research-grade, later)

Bayesian Knowledge Tracing → Deep Knowledge Tracing (LSTM) → embedding error clustering → Item Response Theory → causal inference. Not needed for the MVP.

Concept Mapping

Rules first, embeddings to generalize

Question
  → Rule lookup (question_id → concept)      FOUND? → use it (100% for the question bank)
  → Embedding similarity (≥ 0.65)            else semantic match
  → Flag for teacher review                  else "unmapped question"

Embeddings, simply

Text → vector of numbers capturing meaning. Similar texts → similar vectors. Cosine similarity ≈ "how aligned."

paraphrase-MiniLM-L6-v2 — 384-dim, 80MB, CPU-friendly, Apache 2.0. Multilingual variant covers Hindi/Telugu/Tamil/Bengali/Marathi.

Why rules win here

Deterministic, auditable, zero compute for a curated question bank. Embeddings add flexibility for unseen questions. Hybrid = best of both.

Data & Governance

Datasets, synthetic data, and student privacy

Dataset reality

No public dataset has Indian school assessments with concept tags + error labels. UCI/Kaggle/ASSISTments are foreign or marks-only.

→ Solution: a programmatic synthetic dataset (NCERT Class 5 aligned, 50 students × 6 tests, 6 archetypes).

Student archetypes (demo-critical)

  • A — Fractions difficulty
  • B — Algebra difficulty
  • C — Random mistakes
  • D — Improving over time
  • E — Persistent difficulties
  • F — On track

Privacy (DPDP Act 2023) — not an afterthought

  • Pseudonymized IDs (Student_001) — no names, DOB, addresses, biometrics.
  • No tracking / behavioural monitoring / ads for children (Section 9).
  • Verifiable parental consent in production (Sec 9) · data minimization · purpose limitation · 2-year retention.
  • Approved language only: "possible learning gap" · "may benefit from support" · "confidence: X%" — never "weak"/"will fail".
Testing

Prove the system works — not just that it runs

Functional

  • CSV import edge cases (encoding, duplicates, malformed rows)
  • Scoring normalization (±0.01 tolerance)
  • Error classification per taxonomy category
  • Gap-detection threshold boundaries

AI evaluation

  • Concept mapping ≥90% on labeled set
  • Classification precision ≥85%
  • Confidence calibration: Brier < 0.15
  • LLM hallucination rate < 2%; consistency on repeat runs
Ground truth: a golden set of ~200 human-labeled records (questions → concepts; answers → error types; histories → gap yes/no) powers regression tests and threshold tuning.
Edge Cases

Tested edge cases — because the demo will hit them

Data edge cases

  • Duplicate student IDs
  • Empty / all-correct / all-wrong answer files
  • Question ID not in bank
  • Non-standard answer strings
  • Concept mismatch (embedding low confidence)

Behavior edge cases

  • Single assessment (fewer than 2 → "initial indication")
  • Errors below threshold → shown but not flagged
  • LLM down / offline → rule-based flow still works
  • Teacher approves then rejects intervention → clean states
Honesty rule: every edge case has a defined output; "insufficient data" is a first-class result, never a crash or a guess.

  2. Used official/primary sources: sih.gov.in, pib.gov.in, udiseplus.gov.in, ndear.gov.in, diksha.gov.in, indiacode.nic.in (DPDP Act), asercentre.org.
  3. Labeled evidence: every claim marked verified fact / strong inference / flagged assumption — SIH rules were not invented; gaps were explicitly stated.

Step 2 — Gap analysis

Compared existing systems on a capability matrix → isolated the genuine gap: longitudinal concept-level error-pattern intelligence for teachers.

Step 3 — Design for a beginner

  1. Split architecture into 3 scopes (MVP → SIH → production) so only buildable things are attempted.
  2. Chose the minimum sensible stack; justified every tool; deferred Docker/K8s/React/ML to post-SIH.
  3. Designed deterministic algorithms (mistake fingerprinting, Wilson confidence, intervention loop) before any LLM — AI is the explanation layer, not the decision maker.
  4. Built the learn-while-building roadmap (weeks 1–10) and a concrete first-7-days plan.
